## Decisions

- The frontend is React + Vite + JavaScript with plain CSS.
- Supabase and Netlify are the approved backend and hosting platforms.
- The supplied dark/orange mobile design references are the visual source for the responsive application shell.
- The browser Supabase client uses `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`. It remains `null` until both are configured.
- The Milestone 2 migration creates the complete approved relational schema, but feature-table browser access remains unavailable until Milestone 3 introduces reviewed RLS policies.
- The only Milestone 2 Data API grant/policy lets authenticated users read their own profile, which is required to restore a session and expose the current role.
- The first administrator is promoted manually through the Supabase Dashboard SQL Editor after their Auth user and default trainer profile exist. Browser-based user administration is deferred to Milestone 3.
- Milestone 3 uses explicit authenticated table grants combined with RLS policies. Grants alone do not authorize access.
- Milestone 3 authorization helpers are `SECURITY DEFINER` functions in the non-Data-API `private` schema. The schema grants authenticated callers only the usage and helper execution needed for RLS evaluation.
- The `admin-users` Edge Function validates the caller's JWT and independently checks for an active administrator profile before using a server-side client configured from `SUPABASE_SECRET_KEYS`.
- Secure onboarding extends the `admin-users` authorization check to require `onboarding_completed_at`. Invitations use only the server-configured `APP_URL` origin and redirect to `/set-password`; browser requests cannot supply the redirect target.
- Student-group junction rows represent current membership in Milestone 4. Removing a student from a group deletes the row; the existing `joined_on` and `left_on` columns remain unchanged and have no new historical semantics.
- Group-trainer and student-group changes use reviewed public RPCs so exact-set reconciliation is atomic. The RPCs retain the existing database constraints and do not expose the private RLS helper schema.
- Milestone 5 establishes an authoritative single-row `school_settings` record. The forward-only migration refuses to choose among duplicate settings rows, bootstraps Insane Dance Center with `Europe/Bucharest` only when no row exists, validates the configured IANA timezone, and prevents future duplicate settings rows.
- The follow-up Milestone 5 settings-lifecycle migration prevents deletion of the authoritative settings row, validates every future timezone write against PostgreSQL timezone names, and locks timezone changes once schedule data exists.
- Calendar conversions are centralized in `src/utils/scheduleDateTime.js`. The configured authoritative school timezone controls display and school-local date/time conversion; browser-local date parsing is not used as the conversion authority.
- Calendar entry values that fall in DST spring-forward gaps or fall-back repeated intervals are rejected with actionable feedback. Schedule entries must begin and end on the same local school date.
- Concrete `class` entries require a group, responsible trainer, and room through both frontend validation and the `schedule_entries_class_requires_references` database check. Other entry types may omit those relationships.
- Room and trainer conflicts are enforced by distinct partial PostgreSQL exclusion constraints using half-open `tstzrange` intervals. Cancelled entries do not block slots; adjacent entries remain valid.
- Attendance is linked only to concrete, started, non-cancelled `class` entries. Recovery is an eligible same-group attendance status and never creates cross-group relationships or compensates an earlier absence.
- Attendance eligibility uses current group membership when a record is created. Persisted records remain visible and editable by the responsible trainer after later membership removal; historical unmarked membership cannot be inferred because membership history remains deferred.
- Competition detail display names are supplied by authenticated-only, active-user-checked SECURITY DEFINER RPCs scoped to each competition's associations. They expose no student contact fields; participant current-group information is intentionally omitted rather than broadening membership visibility.
- Competition results use atomic result/member reconciliation RPCs and deferred constraint triggers: individual results require one enrolled participant, team results require at least two, and members retain their competition ID for database-enforced participant linkage.
- Dashboard attendance rates use only recorded `present` and `absent` marks for past, non-cancelled class entries in an explicit school-local date range. Recovery marks and unmarked attendance are excluded rather than inferred.
- Attendance reports use authenticated-only, `SECURITY DEFINER` RPCs with an empty `search_path`. Administrators receive school-wide qualifying historical classes; trainers receive only classes whose stored `schedule_entries.trainer_id` is their caller-derived `private.current_trainer_id()`.
- Attendance report date ranges are inclusive Europe/Bucharest local dates, converted to a half-open UTC timestamp range. They require both dates, permit at most 366 inclusive days, and exclude cancelled or future classes.
- Student report rows are historical `student_id × schedule_entries.group_id` aggregates with persisted marks only; inactive students and students removed from current group membership remain visible when records exist. The report never derives historical attribution from `student_groups`.
- Attendance rate is `present / (present + absent)`. Recovery and unmarked attendance are excluded, and a zero denominator returns `NULL`.
- Group reports distinguish current active student membership from distinct historically recorded students, and distinguish started non-cancelled classes from entries explicitly marked `completed`.
- Student report pagination uses ascending `(group_name, student_display_name, group_id, student_id)` keyset order. Its opaque base64 JSON cursor encodes those four final-order values; page size defaults to 25 and is bounded to 1–100.
- A student-report empty result array means there are no matching rows or the supplied cursor is exhausted. Clients must treat `[]` as the terminal page.
- For a non-empty student-report page, clients read `has_more` from the final row. When it is true, they send that final row's `next_cursor` in the next request; when false, `next_cursor` is `NULL` and no further request is made.
- Student-report keyset pagination is not a database snapshot across requests. Student/group name changes, attendance mutations, and newly qualifying aggregate rows can change report contents or ordering between pages; this MVP limitation is accepted.
- Attendance trends support only monthly Europe/Bucharest calendar buckets, emit zero-count months, and reject otherwise-valid detailed ranges that touch more than 12 calendar months rather than silently truncating them.
- Trainer activity reports are authenticated-only aggregate RPCs. Administrators can report all historical class trainers or filter one trainer; trainers are restricted to their caller-derived historical `schedule_entries.trainer_id`, even after current group assignment removal.
- Trainer activity distinguishes started non-cancelled classes, explicitly completed classes, future non-cancelled classes, and cancelled classes. Attendance uses persisted marks only; recovery is excluded from the `present / (present + absent)` rate. The RPC rejects queries with more than 50 qualifying trainer rows rather than silently truncating them.
- Competition report visibility is narrower than the Competition module: administrators see all qualifying competitions, while trainers see only competitions linked to their caller-derived trainer ID through `competition_trainers`.
- Competition result detail has one row per result entry, plus one row with `NULL` result fields for a qualifying competition with no results. Enrollment counts are distinct enrolled students per competition and are independent of result/member joins; team results remain one result entry. `result_member_display_names` contains at most 50 deterministically ordered `{student_id, display_name}` objects, while `result_member_count` is authoritative for the full member count. The frontend must treat a `result_member_display_names` JSON array length smaller than `result_member_count` as truncation: displayed members are incomplete and may be presented as “Showing 50 of 65 members,” never as the full list.
- Competition participation trends count distinct enrolled students within each calendar month, not summed per-competition counts. Enrollment is not confirmed attendance.
- Competition result pagination uses ascending `(competition_date, competition_id, has_result, result_id)` keyset order and follows the established final-row cursor/terminal-empty-page contract; it is not a cross-request database snapshot.
- The authenticated `/app/reports` frontend uses an explicit Apply/Reset workflow for school-local date and optional authorized-group filters. The default period is the last 30 inclusive calendar days; both dates are required, ranges are capped at 366 days, and chart requests additionally reject ranges touching more than 12 calendar months.
- Attendance report queries are user-and-role scoped TanStack Query entries with 5-minute freshness, 15-minute garbage collection, no polling, and no window-focus refetch. Student report pages retain only local keyset cursor history for Previous navigation and reset to the first page after an applied filter change.
- Reports use the deployed attendance RPCs only. Browser code never sends trainer identity, derives aggregates, or expands visibility beyond the server-authorized response.
- The current student API has no bounded authorized search. The Reports frontend intentionally does not load an unbounded student list merely to populate a selector; student filtering remains unavailable until a bounded server-side search contract exists.
- Session loss, explicit sign-out, and authenticated-user switches cancel then remove user-scoped Reports queries before removing Dashboard queries. This prevents an in-flight report response from repopulating the shared query cache after access ends.
- Reports validate applied table ranges and monthly chart ranges independently. Tables accept all valid inclusive ranges through 366 days; a valid range touching more than 12 calendar months continues to load table data while the chart RPC is skipped with an explicit chart-only message.
- An empty initial Student Attendance page shows the normal empty state without pagination. An empty continuation page shows terminal feedback, disables Next, and retains Previous navigation using the existing local cursor history.
- Trainer Activity and Competition Results share the authenticated Reports route and use their deployed aggregate/reporting RPCs directly. Their query keys include the authenticated user, role, report type, applied dates, relevant filters, page size, and keyset cursor.
- Trainer filtering is intentionally unavailable because no bounded authorized trainer-search API exists. The browser supplies no trainer ID, so trainers remain backend-scoped to their own historical activity and administrators receive the bounded server result or a controlled over-50-trainer error.
- Competition filtering intentionally supports bounded enum status/result-type filters but not a competition dropdown because the existing competition list API is unbounded. Competition Results preserve one row per result, retain no-result rows, use final-row keyset pagination, and never fetch extra member or student data.
- Competition member display uses only the returned `{ student_id, display_name }` JSON. Lists remain collapsed by default, and a returned length below `result_member_count` explicitly states “Showing N of M members.”
- Competition Participation Trend uses the server-provided monthly series, preserves zero months, describes enrollments as distinct monthly enrolled participants rather than attendees, and applies the 12-touched-month limit independently of Competition Results table validity.
- Reports CSV export uses applied filters only and starts paginated Student Attendance and Competition Results exports from a null cursor with sequential 100-row requests. Exports stop at 5,000 data rows, reject malformed or repeated cursors, and never download partial data after errors or cancellation.
- CSV uses UTF-8 BOM, comma delimiters, CRLF line endings, stable human-readable columns, and quoted field escaping. Untrusted text with leading whitespace/control characters followed by `=`, `+`, `-`, or `@` is prefixed with an apostrophe before CSV quoting to prevent spreadsheet formula interpretation.
- One client-side export runs at a time. Cancellation prevents additional page requests, CSV generation, and download; active exports are cancelled on report-tab, authenticated-user, and component lifecycle changes.
- Mandatory onboarding uses the server-owned `profiles.onboarding_completed_at` state. Authenticated but incomplete users are restricted to `/set-password`; protected application routes redirect there, while completed active users retain the normal dashboard flow. The setup page submits only through Supabase Auth password update, explicitly reloads the profile, and navigates only after the server confirms completion. Password recovery remains `/reset-password` and also refreshes the profile before returning to the application.

## Known limitations

- The initial profile trigger assigns the safe `trainer` role. The first administrator must be promoted manually as documented.
- The Edge Function requires Supabase-managed `SUPABASE_URL` and `SUPABASE_SECRET_KEYS`. Secret keys must remain server-side and must never be configured as a `VITE_*` value.
- Group membership history remains intentionally deferred. Historical attendance preserves recorded rows after membership removal, but cannot reconstruct unmarked historical roster cells for removed students.
- Before remote Milestone 5 use, review and apply both Milestone 5 migrations. The first intentionally stops if duplicate `school_settings`, incomplete existing classes, or existing non-cancelled room/trainer overlaps require manual correction; the second hardens the authoritative settings lifecycle required by Calendar.
- Competition participant removal has no separate audit history. Once all current participant rows are removed, the database permits permanent competition deletion.
